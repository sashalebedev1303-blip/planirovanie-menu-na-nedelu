# Чек-лист перекрёстного ревью соседней командой (ЛР-6, шаг 8)

Перекрёстное ревью — это ревью кода **соседней командой**: студент из другой
команды смотрит наш pull request свежим взглядом и оставляет комментарии
в web-интерфейсе GitHub (вкладка **Files changed**), затем ставит решение
кнопкой **Approve** или **Request changes**. Все решения фиксируются в PR.

## Что ревьюить

Предлагаемый PR для внешнего ревью:
[**#110 — Рефакторинг стратегии экспорта по SOLID (OCP) и отчёт «до — после»**](https://github.com/sashalebedev1303-blip/planirovanie-menu-na-nedelu/pull/110).

Открыть PR → вкладка **Files changed** → комментарий к строкам по чек-листу
ниже → кнопка **Review changes** → **Approve** / **Request changes**.

## Чек-лист внутреннего ревьюера (по методичке ЛР-6)

- [ ] Решает ли изменение свою задачу (сюда ли отнесены правки и ничего лишнего)?
- [ ] Понятны ли имена (`ExportStrategy`, `get_strategy`, `STRATEGIES` — понятно ли без чтения кода)?
- [ ] Нет ли дублирования (не осталось ли копий старых классов в `main.py`)?
- [ ] Обработаны ли ошибки (недопустимый формат запроса, пустой список покупок)?
- [ ] Есть ли проверка на новое поведение (как проверить `/api/shopping/export/strategy`)?

## Чек-лист расширенный (стиль и целостность)

- [ ] Код соответствует стандарту команды (ruff чист, `ruff check .` зелёный);
- [ ] Изменение закрыто для изменения, открыто для расширения (OCP): новый
      формат = новый класс + строка реестра;
- [ ] Единая ответственность модулей (SRP): маршруты не знают деталей форматов;
- [ ] Документация обновлена и не противоречит коду (`docs/refactoring.md`);
- [ ] CI (Ruff Linter) зелёный на последний коммит.

## Как оформить итог

1. Каждое замечание — комментарием к конкретной строке, с обоснованием
   (вопрос или предложение, а не оценка автора).
2. Решение — **Approve** или **Request changes**; каждая ветка обсуждения
   закрывается **Resolve conversation** после правок.
3. После ревью соседней команды добавить короткую заметку в конец
   [docs/pull-requests-history.md](pull-requests-history.md): кто ревьюил,
   что найдено, что исправлено.

## Авто-подстановка итогов (по желанию)

Итог внешнего ревью можно оформить прямо в комментарий PR #110 (например,
«Кросс-ревью от команды X: замечание про…, исправлено в …»)
