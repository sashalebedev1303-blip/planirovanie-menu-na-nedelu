# Что осознанно оставляем и почему (docs/debt/accepted-debt.md)

ЛР-8, шаг 6. Инженерное обоснование остаточного технического долга.
Каждая позиция — не «забыли», а «решили не делать сейчас», с условием
возврата. Учитывает сроки проекта (релиз ЛР-8/9 — текущий семестр).

## О-1. HTML-шаблон UI встроен в `main.py` (~1600 строк, позиция Д-5)

**Что:** весь интерфейс (HTML + CSS + JS) живёт строкой внутри
`/` маршрута `main.py` — 64 % файла.

**Почему не сейчас:** извлечение в отдельный файл требует
`--add-data` в сборке PyInstaller и проверки exe-сборки на всех
машинах команды; ближайший релиз (ЛР-9, текущий семестр) менять UI не
планирует. Правки UI в ближайших неделях не предвидятся — выгода от
выноса сейчас меньше риска сломать сборку релиза.

**Возврат:** ЛР-9 (текущий семестр) при следующей доработке интерфейса.

## О-2. `get_report` — своя агрегация вместо переиспользования
`shopping_calc.aggregate_ingredients` (замечание З-9)

**Что:** сводка отчёта считает только числовые количества и возвращает
числа; список покупок агрегирует и «по вкусу», и форматирует строки.

**Почему не сейчас:** объединение изменит контракт ответа
`/api/report`, на который завязан UI (число в таблице). Перед релизом
менять формат ответа без новой итерации тестирования UI — риск.

**Возврат:** при следующей доработке отчёта — заодно с
версионарированием API.

## О-3. Четыре функции с CC 11–12: `_seed_dishes_from_csv` (12),
`apply_favorite` (11), `get_report` (11), `aggregate_ingredients` (11)

**Почему не сейчас:** сложность обусловлена предметной логикой
(парсинг CSV-строк, обработка конфликтов дат, свёртка ингредиентов),
а не запутанностью кода; все четыре покрыты тестами
(`_seed_dishes_from_csv`, `apply_favorite`, `get_report` —
интеграционными сценариями API, `aggregate_ingredients` — модульными
тестами `shopping_calc`, покрытие модуля 100 %) и правок не требуют.
Единый порог команды для обязательного разбиения — CC 10; он одинаков
в `docs/quality/profile.md` и этом документе.

**Возврат:** при любой правке одной из этих функций её CC приводится к
значению ≤ 10 в рамках той же задачи (правило Definition of Done);
при выносе HTML-шаблона (О-1) `_seed_dishes_from_csv` упрощается вместе
с парсингом CSV.

**Уточнение после верификации SonarQube (18.11.2026):** по *когнитивной*
сложности `aggregate_ingredients` даёт 17 при пороге 15 (`python:S3776`),
то есть по метрике SonarQube функция порог превышает. Решение остаётся
в силе (CC и когнитивная сложность считаются по-разному), но при следующей
правке этой функции разбиение обязательно — позиция Д-7 в реестре.

## О-4. SQLite вместо PostgreSQL (позиция «вне топа» реестра)

**Что:** однопользовательский десктоп-режим (данные локально).

**Почему не сейчас:** серверная БД не нужна для сценариев релиза
(16 ч затрат против нулевого эффекта для текущего режима); решение
зафиксировано в ADR-001 и уже осознано командой.

**Возврат:** при многопользовательском кабинете (ЛР-9, текущий семестр).

## О-5. SonarCloud не подключён — локальный статический анализ

**Что:** вместо облачного SonarCloud используется строгий профиль
ruff + собственный скрипт метрик (`scripts/code_metrics.py`);
результаты — в `docs/quality/` (profile, ruff-strict-before/after,
metrics-before/after). Бейдж CI анализатора (GitHub Actions, Ruff
Linter) добавлен в README со ссылкой на прогоны — по шагу 1 методички
«бейдж и ссылку — в README» в той мере, в какой она выполнима без
доступа к аккаунту владельца.

**Почему не сейчас:** SonarCloud требует входа владельца репозитория
(GitHub-аккаунт аналитика) и импорта организации; доступ к веб-
интерфейсу под двумя аккаунтами получить не удалось. Раздел 4.3
методички допускает локальную альтернативу.

**Возврат:** при первом удобном доступе к аккаунту владельца —
подключение SonarCloud к существующим PR (~30 минут по инструкции
в README).
