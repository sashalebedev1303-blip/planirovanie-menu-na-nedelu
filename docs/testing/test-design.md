# Тест-дизайн: агрегация ингредиентов в список покупок (ЛР-7)

**Объект тестирования** — ключевая вычислительная логика приложения:
формирование сводного списка покупок из меню с учётом порций
(`POST /api/shopping/generate`).

**Модуль** — `src/shopping_calc.py` (выделен из маршрута FastAPI по SRP в
ходе ЛР-7, по прецеденту `quantity.py` из ЛР-6):

- `collect_servings(menu_items)` — считает суммарное число порций каждого блюда;
- `aggregate_ingredients(dish_servings, ingredients)` — складывает одинаковые
  ингредиенты, пересчитывает количества на порции и форматирует их;
- `format_quantity(q)` — число → строка (целое без дробной части, дробное —
  через запятую, как принято во всём интерфейсе).

Тест-дизайн выполнен до написания кода тестов: сначала классы эквивалентности
и граничные значения, затем их строки переносятся в автотесты
(`tests/test_shopping_calc.py`, `tests/test_integration_api.py`).

## 1. Классы эквивалентности: количество ингредиента в рецепте

| № | Класс / граница | Вход (quantity × порции) | Ожидаемый результат |
|---|---|---|---|
| 1 | Целое число | `«150»` × 2 | `«300»` |
| 2 | Дробное с запятой | `«50,5»` × 2 | `«101»` |
| 3 | Дробное с точкой | `«50.5»` × 1 | `«50,5»` |
| 4 | Граница дробной части: 0 < q < 1 | `«0,25»` × 2 | `«0,5»` |
| 5 | Нечисловое значение | `«по вкусу»` × 2 | `«по вкусу (x2)»` |
| 6 | Пустая строка | `«»` × 1 | `«»` (позиция сохраняется, без количества) |
| 7 | Граница: целое совпадает с дробным | `«2,5»` × 4 | `«10»` (не `«10,0»`) |

## 2. Классы эквивалентности: группировка ингредиентов

| № | Класс / граница | Вход | Ожидаемый результат |
|---|---|---|---|
| 8 | Один ингредиент в одном блюде | Молоко, 150 г × 3 порции | одна позиция «450 г» |
| 9 | Один ингредиент в нескольких блюдах, разный регистр | «Яйца, 3 шт» + «яйца, 2 шт» | одна позиция «Яйца», «5 шт» |
| 10 | Одинаковый ингредиент, разные единицы | 200 г + 300 мл | две разные позиции |
| 11 | Числовой + текстовый (в разных блюдах) | 100 г И «по вкусу» × 2 | `«100 (+ по вкусу (x2))»` |
| 12 | Название с лишними пробелами | `«  Сыр  »` | `«Сыр»` (пробелы срезаются) |

## 3. Классы эквивалентности: порции блюд

| № | Класс / граница | Вход | Ожидаемый результат |
|---|---|---|---|
| 13 | Блюдо в одном приёме пищи | dish 5, servings 2 | 2 порции |
| 14 | Блюдо в нескольких приёмах — порции суммируются | dish 5 × 2 (обед) + dish 5 × 3 (ужин) | 5 порций |
| 15 | Граница: servings = 0 / None | servings 0 | считается как 1 |
| 16 | Позиция меню без блюда (dish_id = None) | текст «Кофе» | в расчёт не попадает |
| 17 | Граница: ингредиент блюда, не добавленного в меню | dish_id 99 вне меню | позиция отбрасывается |

## 4. Валидация приёма пищи (`POST /api/menu`, см. баг-репорт № 3)

| № | Класс | Вход meal_type | Ожидаемый результат |
|---|---|---|---|
| 18 | Валидное значение | `breakfast` / `lunch` / `dinner` / `snack` | 200, запись сохраняется |
| 19 | Недопустимое значение | `supper` | 422 (запись не сохраняется) |
| 20 | Граница: повторное сохранение той же позиции | dinner → dinner | данные обновляются, дубля нет |

## 5. Интеграционные сценарии (форма → валидация → сохранение → расчёт)

| № | Сценарий | Шаги | Ожидание |
|---|---|---|---|
| I1 | Форма «День меню» — валидация — сохранение | POST /api/menu (неверный meal_type) → POST /api/menu (верный) → GET /api/menu | 422 → 200 → в меню одна обновлённая запись |
| I2 | Форма «Сформировать из меню» — расчёт — список покупок | POST /api/dishes (2 ингредиента) → POST /api/menu (2 порции) → POST /api/shopping/generate → GET /api/shopping | количества пересчитаны с учётом порций, дробное — через запятую, позиции агрегированы |
| I3 | Полный отчёт /api/report (см. баг-репорт № 2) | ингредиент «50,5» × 2 порции → GET /api/report | summary учитывает «50,5» как 101, а не 0 |
