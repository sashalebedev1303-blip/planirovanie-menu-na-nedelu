# Демонстрация «путь изменения» (ЛР-9)

Живой сценарий защиты: показываем, как одно изменение проходит путь
**коммит → pull request → конвейер → артефакт → образ → релиз**. Всё
выполняется на реальном репозитории, скриншоты — только как резервная копия
и приложение к отчёту (методичка: «мёртвые» скриншоты не засчитываются).

## Сценарий на 6 минут (PR подготовлен заранее)

Ветка и PR создаются **до защиты**, чтобы не тратить время аудитории на
ожидание. Вживую показываем только push в готовый PR и перезапуск конвейера.

| Время | Шаг | Действие | Что показывает |
|---|---|---|---|
| 0:00–1:00 | 1 | правка → `git commit` → `git push` в открытый PR | изменение появляется в отдельной ветке, `main` не тронут |
| 1:00–2:00 | 2 | Вкладка **Checks** / **Actions → CI** | job'ы `lint → tests → build → docker` идут по цепочке `needs` |
| 2:00–3:00 | 3 | job `tests` → job `build` → **Artifacts** | 43 теста, покрытие 100 % по ключевым модулям, артефакт `tastyweek-app` |
| 3:00–4:00 | 4 | job `docker` → вкладка **Releases → v1.0.0** | smoke-тест `docker run` + `/api/menu`, тег, заметки, архив |
| 4:00–5:00 | 5 | заранее подготовленный PR со сломанным тестом | красный `tests` блокирует **Merge** — только после включения защиты ветки |
| 5:00–6:00 | 6 | локальный `docker run` (или job `docker`, если Docker нет) | приложение поднимается из того же образа, что собрал CI |

> Если есть запас времени, шаг 1 можно расширить созданием ветки и PR вживую
> (+1,5–2 минуты). При жёстком регламенте этого делать не нужно: важнее
> показать конвейер, артефакт и релиз.

## Подготовка за 15 минут до защиты

1. **Слить PR #128 в `main`** через «Create a merge commit» (не squash), чтобы
   тег `v1.0.0` остался в истории основной ветки.
2. Включить защиту `main` по `docs/ci.md`, п. 3: обязательные проверки
   `lint`, `tests`, `build`, `docker` + 1 approval, запрет прямых push.
3. Проверить, что пакет GHCR виден: открыть
   `Profile → Packages → planirovanie-menu-na-nedelu`. Если пакет приватный —
   либо сделать его публичным, либо заранее выполнить `docker login ghcr.io`.
4. Открыть и оставить во вкладках: PR, прогон CI, артефакт, страницу релиза.
5. Проверить, установлен ли Docker. Если нет — шаг 6 заменить показом job
   `docker` и страницы GHCR: smoke-тест уже выполнен в CI.
6. Прогнать презентацию с таймером: 7 слайдов должны укладываться в 5 минут,
   демонстрация — в 6 минут.

## Резервный вариант (если сеть в аудитории недоступна)

1. Показать локальный прогон: `python -m ruff check .`, `python -m pytest -v`,
   `python scripts/build_release.py`, `docker build`/`docker run`.
2. Открыть заранее скачанные скриншоты из этой папки.
3. Открыть локальный файл `docs/release-notes/v1.0.0.md`.

## Команды для живой демонстрации

```bash
# 1. Изменение и коммит
git switch -c demo/live-path
# ... правка ...
git add -A && git commit -m "docs(lab9): демонстрационное изменение"
git push -u origin demo/live-path

# 2. После зелёного PR — локальная проверка артефакта
python scripts/build_release.py
python -m zipfile -l dist/tastyweek-app.zip

# 3. Локальный запуск образа
docker build -t tastyweek:demo .
docker run --rm -p 8000:8000 -e OPEN_BROWSER=0 tastyweek:demo
curl http://127.0.0.1:8000/api/menu
```
