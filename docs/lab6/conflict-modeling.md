# Шаг 7: моделирование конфликта слияния (ЛР-6)

Целевая ситуация из методички: два участника **намеренно меняют одну
строку общего файла** в разных ветках, воспроизводится конфликт
слияния, он разрешается и пошагово документируется.

## Задачи и ветки участников (шаг 6)

| Ветка | Участник | Задача из бэклога | Содержание |
|---|---|---|---|
| `feature/menu10-export-file` | Игорь Николаев | MENU-10 «Экспорт списка покупок в файл» | раздел README про экспорт + правка строки «Текущая веха» |
| `feature/menu8-testing` | Лебедев Александр | MENU-8 «Провести тестирование основных сценариев» | раздел README «Как проверять» + правка той же строки «Текущая веха» |

Оба брали истории из `docs/scrum/product-backlog.md` (исходные компоненты
функции в коде уже реализованы, поэтому задачи завершались документацией
+ вехой). Оба заядло правили **одну и ту же строку README**:

```
**Текущая веха:** Демонстрация прототипа — 23.10.2026
```

— каждый со своей версией новой вехи.

## Пошаговый протокол (фактические команды и вывод)

1. Ветка Лебедева синхронизирована с main, две задачи закоммичены
   (`e7e92a8`, `fe53859`).

2. Слияние ветки коллеги воспроизвело конфликт:

```
> git merge feature/menu10-export-file
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
```

3. `git status` показал конфликтующий файл c кодом `UU`:

```
UU README.md
```

4. В файле открылись маркеры конфликта — обе версии одной строки:

```
<<<<<<< HEAD
**Текущая веха:** Демонстрация ЛР-6 — 03.11.2026          ← версия меню8 (Лебедев)
=======
**Текущая веха:** ЛР-6 «Реализация и Git-workflow» — 31.10.2026 ← версия menu10 (Игорь)
>>>>>>> feature/menu10-export-file
```

Прочитали обе версии: противоречия по смыслу нет — различие только в
формулировке вехи. Секции «Экспорт списка покупок (MENU-10)» и
«Как проверять (MENU-8)» Git слил автоматически (они в разных местах
файла).

5. Решение: оставить **более раннюю веху — дату демонстрации ЛР-6 —
03.11.2026** (ближайшее предстоящее событие плана), итоговую строку
одну на файл:

```
**Текущая веха:** Демонстрация ЛР-6 — 03.11.2026
```

6. Пометили конфликт разрешённым и зафиксировали слияние:

```
> git add README.md
> git commit -m "Слить menu10-export-file в menu8-testing, сохранив обе
  секции README и актуальную веху"
[feature/menu8-testing 3c9318a] ...
```

7. Порядок слияний в main (шаг 8): сначала PR ветки
   `feature/menu10-export-file`, после Approve — Merge; затем PR ветки
   `feature/menu8-testing` — локальное слияние выше эквивалентно шагу
   «потянуть main после первого PR и разрешить конфликт в ветке второго
   участника», поэтому второй PR сливается кнопкой без ручного разбора.

## Арифметика конфликта: почему он возник

- Git слил **вставки** обоих участников (разные области README) — файл
  содержит обе секции; конфликтовать вставкам не на чем.
- Но строка «Текущая веха» у обоих **изменена** — конфликт содержания:
  одна строка, две версии. Это нормальное следствие параллельной
  работы при GitHub Flow, разрешается читаемым и согласованием
  (см. предыдущий реальный кейс: `docs/conflict-resolution.md`).

Дополнительно: аналогичный конфликт разрешился в веб-интерфейсе GitHub
кнопкой **Resolve conflicts** при слиянии PR #99 (подробно —
`docs/conflict-resolution.md`).
