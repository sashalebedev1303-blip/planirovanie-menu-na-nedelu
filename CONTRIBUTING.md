# Правила работы над проектом «ИС планирования меню на неделю»

Документ описывает обязательные правила командной работы над проектом.
Они действуют с первой лабораторной работы и до защиты сквозного проекта.

## Ветвление

Мы используем GitHub Flow

Основная ветка — `main`. **Прямые коммиты в `main` запрещены.**

Любое изменение — в отдельной ветке с осмысленным именем:

- `feature/<название>` — новая функциональность
  (например, `feature/menu-week-view`, `feature/shopping-list-generator`);
- `docs/<название>` — документация
  (например, `docs/meeting-template`, `docs/readme-update`);
- `fix/<название>` — исправление ошибки
  (например, `fix/duplicate-ingredients`).

Ветка живёт до слияния в `main`, после слияния удаляется.

## Коммиты

Сообщение коммита — в повелительном наклонении, по делу:

- «Добавить форму выбора блюд на неделю»
- «Исправить суммирование повторяющихся ингредиентов»
- «Обновить README с описанием проекта»

Коммит должен решать одну задачу; большие изменения дробятся
на серию небольших коммитов.

## Pull request

Любое изменение попадает в `main` только через pull request (PR).

В PR обязательно:

- заголовок в повелительном наклонении;
- описание: что сделано, зачем, как проверить;
- назначенный ревьюер из команды (не автор PR);
- ссылка на задачу трекера, если есть (например, `Closes #3`).

Ревьюер проверяет изменения и ставит **Approve** или **Request changes**.
Важно: PR не может быть слит в main, пока автоматические проверки (CI / Линтер Ruff) не покажут зеленые галочки.
Только после Approve PR сливается в `main`.

## Версии и теги (ЛР-6)

Версия проекта — по семантическому версионированию `MAJOR.MINOR.PATCH`:

- `MAJOR` — несовместимые изменения модели данных или API;
- `MINOR` — новая функциональность;
- `PATCH` — исправления и правки кода без изменения поведения.

Значимый этап фиксируется аннотированным тегом:

```
git tag -a v0.1.0 -m "Прототип: ключевые сценарии"
git push origin v0.1.0
```

Состав версии публикуется в разделе **Releases** GitHub
(тег + заметки о составе версии, шаблон —
`docs/lab6/release-notes-v010.md`).

## Автоматическая проверка перед коммитом (ЛР-6)

Стандарт кодирования — PEP 8, проверяется линтером **ruff**
(конфигурация — `ruff.toml`). Новый код должен проходить
`ruff check .` без замечаний; CI проверяет это на каждый push
(`.github/workflows/ruff.yml`).

Чтобы замечания ловились до попадания в репозиторий, включите pre-commit
хук с линтером:

```
pip install -r requirements-dev.txt
pre-commit install          # хук запускается на каждый git commit
pre-commit run --all-files  # проверка всех файлов вручную
```

Конфигурация хука — `.pre-commit-config.yaml`: перед коммитом запускается
ruff, наличие замечаний блокирует коммит до исправления.

Тесты нового кода — `pytest` (каталог `tests/`); они же служат
критерием «хорошо/плохо» в `git bisect` (см.
`docs/lab6/bisect-reflog-demo.md`).
